# 开发侧阶段手册

给单位内部平台的开发人员用。每个阶段写三件事：**你做什么、仓库里留下什么、怎样算过关**。

业务功能可以后写。下面这些做完之前，不要把生产当试验场。

## 开发负责什么

| 你负责 | 需要业务配合 | 需要信息中心 / 机房配合 |
| --- | --- | --- |
| 范围写成可开发的场景和数据对象 | 找 3 个真实用户给你看现在怎么干活 | 测试机、生产机、端口、域名/证书 |
| 架构、代码、测试、安装方式 | 确认 v1 做什么、明确不做什么 | 备份落点、内网出站限制、AD/统一身份（如有） |
| 发布、回滚、备份脚本、手册 | 约定发版窗口（避开结账/高峰） | 防火墙、时间同步、磁盘配额 |
| 第二负责人能按手册接管 | 验收主流程是否真的能干活 | 生产密钥只放服务器，不进聊天工具 |

没有第二负责人时，先指定一名能跟着点一遍的同事，手册才算交得出去。

---

## 0. 立项定边界

**目的：** 把口头需求变成能开工的边界。没写清的需求，会在生产里用故障来写清。

**你做什么：**

1. 跟至少 3 个真实用户坐下来，看他们现在用表格、纸质单还是旧系统干活。
2. 写出 3–5 个场景，每个场景包含：谁、在哪台电脑、做什么、成功长什么样。
3. 列出会碰到的数据对象（人、单、设备、文件……）和外部系统（OA、AD、已有库）。
4. 写下非目标：v1 明确不做的功能。
5. 定义上线 30 天可检查的结果（例如“科室能自己完成某类登记，不再找你改 Excel”）。

**仓库里留下：** `docs/scope.md`

**过关：** 范围说明不超过两页，业务和开发都点过头。没有它，不开写业务代码。

**不要做：** 一上来选框架、拆微服务、写花哨原型。

---

## 1. 按运维做架构

**目的：** 先决定系统怎么跑、怎么备份、怎么登录，再铺项目目录。

**你做什么：**

1. 画一张部署图：用户 → Nginx → 应用 → 数据库 → 备份落点。不是类图。
2. 选定团队会的单体技术栈；按业务模块分目录，不要按微服务拆仓库。
3. 定身份方案：本地账号，或对接单位已有登录。角色和操作审计从第一天留位置。
4. 列出全部配置项（数据库、端口、密钥、文件目录），约定密钥不进 Git。
5. 草拟核心表结构，标出唯一键和“谁在什么时候改过”。

**仓库里留下：** `docs/architecture.md`、空的项目目录骨架、配置项清单

**过关：** 新来的同事看图 10 分钟，能说出系统怎么跑、数据在哪、挂了去哪看。

**不要做：** 无专职运维就上 K8s、服务网格、一堆小服务。

---

## 2. 环境与配置分离

**目的：** 代码只构建一次。测试和生产的差异全在配置。

**你做什么：**

1. 用同一套 Compose / 安装方式拉起本地和测试：应用 + 数据库。
2. 提交 `.env.example`（有变量名和注释，没有真实密码）。
3. 接入数据库迁移工具，第一次 schema 就用迁移生成，禁止只在库里手工点。
4. 写清测试环境如何启动、测试账号是谁；生产数据不准进测试。
5. 约定制品名：构建一次，测试用过的那份原样进生产。

**仓库里留下：** `docker-compose.yml`（或同等文件）、`.env.example`、`migrations/`

**过关：** 同事按 README 一条命令能在自己电脑上跑起来；测试包和生产包是同一份。

**不要做：** 生产密码写进代码；测试库里躺真实名单。

---

## 3. 工程纪律

**目的：** 人少更需要纪律，否则生产会变成唯一的测试环境。

**你做什么：**

1. README 写死：如何安装依赖、如何启动、如何跑测试。一条命令能构建。
2. 保护主干：短分支，合并前有人看过（哪怕只有两个开发，也互相看）。
3. 先写这四类测试再堆功能：登录成功/失败、一条主业务流程、无权限被拒绝、迁移能升级。
4. 依赖用锁文件；生产安装禁止 `latest`。
5. 问题先记在 issue / 变更记录，再改代码。

**仓库里留下：** CI 配置、锁文件、`README.md` 启动说明、关键路径测试

**过关：** 空机器拉仓库，按 README 能构建、能测试、失败会红。

**不要做：** 在生产服务器上直接改文件；问题只留在聊天记录里。

---

## 4. 可重复部署

**目的：** “我电脑上能跑”不是部署。部署是别人按文档能复现。

**你做什么：**

1. 只保留一种生产装法：Docker Compose 或 systemd 安装包，写进 `deploy/`。
2. 实现 `GET /health`：进程活着不算，必须能连上数据库才返回成功。
3. 发布时自动跑迁移；迁移失败则停止，不带着半成品库上线。
4. 日志打到标准输出或固定文件，配轮转，避免磁盘被写满。
5. 内网准备离线包：镜像或安装包、依赖、说明一起走。

**仓库里留下：** `deploy/`、`GET /health`、安装说明、离线打包脚本（如需要）

**过关：** 一台新机器对照文档，30–60 分钟装好，health 为绿。

**不要做：** 三种装法并存，只有你记得哪套是真的。

---

## 5. 小步发布与回滚

**目的：** 稳定来自可逆的小变更，不是一年一次的大上线。

**你做什么：**

1. 定版本号（日期或语义化均可），每次发布打 tag。
2. 填发布检查单：改了什么、如何点主流程、失败如何退回上一 tag。
3. 先发测试，按检查单点过登录和主流程，再发生产。
4. 写回滚步骤并演练一次：换回上一制品；若有迁移，写明能否回退、不能回退时如何处理。
5. 发布后观察 30–60 分钟：health、错误日志、主流程、磁盘。

**仓库里留下：** `docs/release-checklist.md`、回滚步骤、changelog / tag

**过关：** 任意一次失败，能在约定时间内退回上一版。

**不要做：** 月底结账窗口发版；回滚写着“到时候再说”。

---

## 6. 观测、备份、告警

**目的：** 没演练过的备份，只是一份让人安心的假文件。开发要把这些写成脚本，不要口头交代。

**你做什么：**

1. 写 `scripts/backup.sh`：备份数据库和关键文件，输出带日期的文件。
2. 写 `scripts/restore.sh`，在测试环境跑通一次，记下耗时。
3. 日志带时间、用户、动作，能追到“谁在什么时候改了什么”。
4. 告警只留三条且有人接：服务挂（health 失败）、磁盘满、备份失败。
5. 把证书、域名、依赖到期日写进日历，到期前 30 天处理。

**仓库里留下：** `scripts/backup.sh`、`scripts/restore.sh`、最近一次恢复演练记录

**过关：** 抽一天，只靠备份，能在测试机把系统找回。

**不要做：** 只做备份不做恢复；日志没有用户和动作。

---

## 7. 手册、演练、交接

**目的：** 系统寿命取决于交接，不取决于你还在不在岗。

**你做什么：**

1. 写安装说明：机器、系统、端口、反向代理、数据库、第一个管理员怎么建。
2. 把发布检查单和回滚步骤放进仓库，不要放私人笔记。
3. 写故障 1-2-3：服务挂了看哪、磁盘满了怎么清、数据库起不来怎么恢复。
4. 列出管理员账号（禁止共用一个大密码），以及证书/域名到期表。
5. 指定第二负责人，让他只靠手册完成一次安装或一次发布。

**仓库里留下：** `docs/runbook.md`、账号与到期表（不含密码）、第二负责人演练记录

**过关：** 第二个人只靠手册，能完成一次发布和一次恢复。

**不要做：** 密码发在群里；手册只在你的电脑上。

---

## 上线门禁（开发自己卡住）

六条全过才把制品交给生产。功能做完但门禁没过，只是把风险搬了个地方。

1. `docs/scope.md` 还在，且和现在做的一致。
2. 测试环境用的就是将要上生产的那份制品。
3. `/health` 为绿，主流程在测试环境点过。
4. 备份恢复在测试环境成功做过一次。
5. 发布单上有可执行的回滚步骤。
6. 手册和第二负责人已经走一遍。

---

## 建议的仓库目录

业务代码按你们的技术栈放。下面这些是过程要求必须出现的位置：

```
docs/scope.md                 # 阶段 0
docs/architecture.md          # 阶段 1
docs/release-checklist.md     # 阶段 5
docs/runbook.md               # 阶段 7
.env.example                  # 阶段 2
migrations/                   # 阶段 2
deploy/                       # 阶段 4
scripts/backup.sh             # 阶段 6
scripts/restore.sh            # 阶段 6
README.md                     # 阶段 3：一条命令能跑
```

先把目录建起来，再写第一行业务功能。
